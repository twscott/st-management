## 🎯 设计决策说明

### 1. 为何选择 Blazor Server 而非 WASM？
- **原因**: 需要实时日志更新，且 SignalR 在 Server 模式下表现更好
- **验证**: WebSocket 连接稳定，消息传递延迟 < 100ms

### 2. 为何日志使用内存存储而非 EF Core？
- **原因**: TimerExecutionLog 是临时执行记录，无需持久化到数据库
- **实现**: TimerExecutionLogService 单例服务，max 1000 条记录自动清理
- **权衡**: 内存占用 ~5MB（1000条记录），可配置

### 3. 为何 @rendermode 是关键？
- **问题**: 没有 @rendermode 指令的 Blazor 页面会变成静态页面
- **结果**: @onclick 事件处理器不执行，页面变成纯 HTML
- **解决**: `@rendermode InteractiveServer` 启用客户端事件绑定和 WebSocket 通信

### 4. 为何任务名称需要带连字符？
- **原因**: ITimerTask 实现类中 Name 属性返回带连字符的名称
- **示例**: `public string Name => "SST-Processing";`
- **映射**: TimerManager 构造函数通过 `t.Name` 构建字典 key

## 🐛 已知问题与局限

### 1. 浏览器缓存导致任务名称错误 🔴
**问题**: 用户浏览器仍在使用旧编译的 Blazor 代码
**症状**: 
- 日志显示 "手動觸發任務: SSTProcessing"（无连字符）
- 虽然源代码已修正为 "SST-Processing"

**根原因**: Blazor 框架将页面编译为 JavaScript 并缓存到浏览器
**解决方案**:
```
用户需执行:
1. 按 Ctrl+Shift+Delete 打开"清除浏览数据"
2. 选择"所有时间"和"Cookies及缓存文件"
3. 按 Ctrl+Shift+R 强制刷新
4. 重新访问 http://localhost:5089
```

**预期结果**: 浏览器会重新下载最新的 Blazor 代码，任务名称将正确显示并正常执行
